Column Row Pipeline Roadmap

Status: Implementation roadmap for Column Row Pipeline Design.

Phases 1-6 and 9a-9g are implemented. Phase 7 and preset-library work (Phase 10) remain planned.

This roadmap breaks the per-column row-pipeline refactor into small, testable steps. The design goal is to let each tensor column derive its own row-aligned gather inputs through TransformPipelines while keeping GatherResult a container/direct-gather executor rather than a pipeline runner.

End State

The refactor is complete when:

  • ColumnRecipe has an optional row_pipeline_json field.
  • TensorDesign JSON parse/serialize round-trips row_pipeline_json.
  • Empty row_pipeline_json preserves the current full-interval behavior.
  • A row pipeline can produce DigitalIntervalSeries windows that are passed to GatherResult as prepared windows.
  • A column pipeline can receive row-specific values through PipelineValueStore, such as one normalization event per row.
  • Per-column gather geometry can differ across columns while row identity and RowDescriptor remain tied to the original row source.
  • Onset-window spike presence and onset-sampled analog covariates are expressible in JSON.
  • Common workflows are available through discoverable presets so users do not need to remember raw transform or binding keywords.
  • The temporary pipeline_json "offset" sample-at-offset path is removed or replaced by row-pipeline behavior.
  • Tests cover identity behavior, onset windows, point sampling, overlapping windows, cross-timeframe gather, and invalid row-count changes.

Current Inventory

Implemented foundations:

  • GatherResult::create(source, windows, alignment_points) accepts prepared windows and optional alignment events for existing direct-gather consumers.
  • GatherResult::fromRows() and fromRowsLike() support row-aligned DataObject results from external pipeline helpers.
  • DigitalIntervalSeries::createOverlapping() preserves overlapping gather windows.
  • IntervalToEvent converts interval rows to events.
  • EventToInterval converts events to overlapping windows.
  • PruneOverlappingIntervals provides explicit keep-first overlap pruning.
  • buildIntervalPipelineProvider() gathers over interval rows and applies range reductions.
  • buildPipelineColumnProvider() handles timestamp-row columns.
  • TensorDesignBuilder builds lazy-column tensors from JSON.
  • ColumnRecipe::row_pipeline_json is parsed and serialized.
  • resolveIntervalGatherWindows() resolves identity and DigitalIntervalSeries row-pipeline output.
  • buildProviderFromRecipe() uses row-pipeline windows for interval-row columns.
  • Digital event/interval views expose ClockTicks-based API-facing elements.
  • PipelineValueStore stores ClockTicks, and NormalizeTimeParamsV2::alignment_time is ClockTicks.
  • gatherAndExecutePipeline() executes JSON-loaded pipeline steps, including container steps, on each gathered row before applying the terminal range reduction.
  • NormalizeDigitalEventSeriesRelative normalizes a gathered DigitalEventSeries into relative ClockTicks storage while preserving event EntityIds.
  • ColumnRecipe::pipeline_value_bindings is parsed, serialized, and used to bind one row-aligned DigitalEventSeries value into PipelineValueStore per tensor row.
  • Direct binding sources from DataManager keys and derived binding sources using source_pipeline_json are supported when they resolve to row-aligned DigitalEventSeries objects.
  • Interval-row columns can dispatch DigitalEventSeries row-pipeline output as sample times for timestamp-style providers.
  • ShiftDigitalEventSeries shifts DigitalEventSeries sample times and replaces the temporary top-level pipeline_json "offset" compatibility path.
  • Angle-at-contact-onset point sampling is tested through TensorDesign JSON in the whisker-contact scenario.
  • Contact-aligned spike presence is tested through TensorDesign JSON in the whisker-contact scenario.

Known gaps:

  • There is no row-pipeline caching.
  • UI does not expose row-pipeline configuration.
  • The Phase 9c column recipe preset registry exists with a compiled preset set and TensorDesigner Add Preset… support.
  • The Phase 9d design authoring preset registry exists with a compiled whisker_contact_feature_table preset and TensorDesigner Apply Table Preset… support.
  • There is no broader preset JSON/file library yet.

Phase 5: Iterable PipelineValueStore Bindings

Status: done. The gathered-row execution path supports container-step pipelines before terminal range reduction, NormalizeDigitalEventSeriesRelative provides container-level DigitalEventSeries -> DigitalEventSeries normalization, and pipeline_value_bindings supplies row-specific ClockTicks values through PipelineValueStore.

Goal: supply per-row values to pipeline_json transforms through the existing TransformsV2 PipelineValueStore mechanism without making row_pipeline_json responsible for normalization markers.

Motivating example: gather Spikes into one DigitalEventSeries per trial/contact interval, then execute a TransformPipeline containing NormalizeTime on each gathered row. The normalization time comes from a row-aligned DigitalEventSeries, such as ContactOnset, or from Contact -> IntervalToEvent(start). The event for row i is written into PipelineValueStore as ClockTicks and bound to the NormalizeTime parameter for row i.

Tasks:

Completed tasks:

  1. Allow gathered row execution to run JSON-loaded container steps before terminal range reduction.
  2. Add NormalizeDigitalEventSeriesRelative as the container-level normalize transform for gathered DigitalEventSeries rows.
  3. Cover container-step-before-reduction behavior with a TensorColumnBuilders test using EventCountInWindow after normalization.
  4. Define a JSON schema for iterable bindings from DataObjects into PipelineValueStore keys: pipeline_value_bindings[] with source_key, optional source_pipeline_json, and store_key.
  5. Support direct iterable sources from DataManager keys with implicit identity source pipeline.
  6. Support derived iterable sources from a DataManager key plus source_pipeline_json.
  7. Start with DigitalEventSeries binding into PipelineValueStore as ClockTicks from the event returned by DigitalEventSeries::view().
  8. Defer DigitalIntervalSeries binding. Use IntervalToEvent in source_pipeline_json for start/end/center selection.
  9. Build one store value per tensor row from the resolved iterable DataObject.
  10. Inject the current row’s values into PipelineValueStore before applying pipeline_json parameter bindings.
  11. Verify a normalize-time transform uses the bound store value, not the gather window start.
  12. Add raster/PSTH-style tests where spikes are gathered in trial windows and normalized to a separate event per row.
  13. Add row-count mismatch tests for direct iterable sources.

Exit criteria:

  • Per-row transforms can consume a marker that is outside the gathered DataObject through parameter bindings.
  • Trial-relative transforms can consume correct marker times.
  • Iterable binding sources are explicit and row-count checked.
  • Direct-key iterable bindings and key-plus-pipeline iterable bindings are both covered by tests.
  • NormalizeTime accepts a ClockTicks binding and subtracts in clock-tick coordinates.
  • Phase 5 tests use the same DataObject view() element types that normal TransformPipeline execution uses.

Settled design choices:

  • Iterable binding declarations live on ColumnRecipe, beside pipeline_json.
  • source_pipeline_json uses the same PipelineDescriptor schema as row_pipeline_json and pipeline_json.
  • Iterable binding store_key values must not overwrite other keys; duplicates are rejected.
  • Temporal iterable values should be bound as ClockTicks, not raw TimeFrameIndex values.
  • PipelineValueStore stores ClockTicks directly.
  • NormalizeTimeParamsV2::alignment_time is ClockTicks and binds through ClockTicksReflector.
  • NormalizeClockTicksValueV2 is the canonical pipeline transform for DigitalEventSeries value projections; ClockTicksWithId is reduced to ClockTicks by the projection helper before pipeline execution.
  • NormalizeDigitalEventSeriesRelative is the canonical container-level transform when the gathered row should remain a DigitalEventSeries with relative ClockTicks values before reduction or export.
  • Existing PipelineValueStore, parameter bindings, and gather extension helpers should be reused or generalized to bind iterable values per row.
  • User-facing presets should hide the distinction between ClockTicksWithId and ClockTicks normalize transforms whenever possible.

Test Coverage Notes

Current row-pipeline coverage is split across four files:

  • tests/TransformsV2/test_tensor_column_builders.test.cpp covers the TransformsV2 provider layer, resolveIntervalGatherWindows() behavior, and Phase 5 direct/derived pipeline_value_bindings execution.
  • tests/TensorDesign/test_tensor_design_builder.cpp covers TensorDesign JSON parsing, serialization, JSON-to-tensor builds, and Phase 5 end-to-end bound normalization through fully specified JSON.
  • tests/TransformsV2/test_tensor_whisker_contact_scenario.cpp covers programmatic provider/lazy tensor construction over the whisker-contact fixture.
  • tests/TensorDesign/test_tensor_whisker_contact_scenario.cpp covers the TensorDesign JSON path over the same fixture, including contact-aligned spikes.

The two whisker-contact files are not exact duplicates. They exercise different architectural layers. The older TransformsV2 file does not validate row_pipeline_json; it remains useful as lower-level integration coverage, though it may be a candidate for reduced assertions if runtime becomes an issue.

Potential stale or missing coverage after Phase 8:

  • DigitalEventSeries row-pipeline output rejection is covered at the row-geometry/helper layer; add a TensorDesign JSON-level rejection test if error messages become part of the user contract.
  • Add explicit tests for malformed but non-empty row_pipeline_json at the TensorDesign JSON build layer if not already covered by provider tests.
  • Add a derived binding row-count mismatch test if direct mismatch coverage is not considered sufficient.
  • Add cache behavior tests when row-pipeline caching is introduced.

Phase 9d: Design Authoring Presets

Status: done for the initial compiled design authoring preset registry and motivating whisker-contact table preset.

Goal: support reusable whole-table authoring templates that set row source and add multiple related column groups, while preserving expanded raw TensorDesign JSON as the executable and saved-analysis format.

Design authoring presets are a higher-level convenience layer than Phase 9c column presets. A column preset expands to one or more ColumnRecipes and appends them to the current design. A design authoring preset expands to a row source plus a set of raw ColumnRecipes, producing an ordinary TensorDesignSpec immediately after application.

Design preset invocations should not become the single source of truth for reproducible analysis. They are authoring shortcuts only. After applying a design preset, saving should write the expanded row_source and columns fields, not the preset invocation. Loading and executing a saved design should not require the design preset registry.

Tasks:

  1. Define a DesignPresetExpansion shape containing row-source fields plus multiple raw ColumnRecipes. Done.
  2. Add a compiled whisker_contact_feature_table authoring preset covering curvature, spike count, onset spike presence, angle at onset, and optional keypoint x/y columns. Done.
  3. Add tests comparing design preset expansion to the equivalent raw TensorDesign JSON. Done.
  4. Prefer compiled expansion functions initially for design presets that need loops or complex defaults. Done.
  5. Ensure applying a design preset produces an ordinary TensorDesignSpec and that serializeDesignJson() writes expanded raw fields only. Done.
  6. Add TensorDesigner UI affordance such as New From Preset… or Apply Table Preset…. Because this changes the row source, the UI should confirm replacement when the current design already has a row source or columns. Done.

Exit criteria:

  • A complete motivating analysis table can be authored from one preset plus a small parameter form.
  • Column presets remain useful for incremental table editing.
  • Applying a design preset produces ordinary row-source and column recipe JSON that can be saved and executed independently of the preset registry.

Phase 9e: Decoupling Row Modifiers and Column Aggregators

Status: done.

Goal: Prevent combinatorial explosion of monolithic presets (e.g., analog_sample_at_interval_start, event_presence_around_interval_start) by splitting the registry into two composable domains: Row Modifiers and Column Aggregators.

Tasks:

  1. Introduce RowModifierRegistry. This registry provides descriptors that output row_pipeline_json and declare the resulting Effective Row Type (e.g., Interval -> Event, Interval -> Interval). Done. RowModifiers also support emitting pipeline_value_bindings.
  2. Introduce ColumnAggregatorRegistry. This registry provides descriptors that output pipeline_json and optional pipeline_value_bindings. These are filtered based on the Effective Row Type and Target Data Type. Done.
  3. Refactor ColumnRecipePresetRegistry (or create a UI “Stitcher” equivalent) to seamlessly combine a selected Row Modifier and a Column Aggregator into one or more ColumnRecipes. Done. Handled natively in TensorDesignBuilder json parsing.
  4. Carefully untangle multi-input presets (like multi_point_xy_at_interval_start): Done.
    • The UI Stitcher must handle cases where the Column Aggregator accepts a list of source_keys (e.g., multiple keypoints).
    • For each input key, the Stitcher generates a distinct ColumnRecipe, applying the same row_pipeline_json (from the Row Modifier) to each.
  5. Create a two-step UX flow in TensorDesigner: (Deferred to UI layer)
    • Step A (Optional): Select a Row Modifier (filtered by top-level row strategy).
    • Step B (Required): Select a Target Data Series and Column Aggregator (filtered by the Effective Row Type from Step A).
  6. Write tests ensuring that a composed Modifier + Aggregator yields the exact same JSON as the older monolithic presets. Done.

Exit criteria:

  • Users can independently mix and match row gather geometry (like “Onset Window”) with data extraction logic (like “Mean”, “Event Count”) without requiring a custom C++ preset for every combination.
  • Multi-input workflows (like expanding 5 keypoints at interval onset) remain fully supported and generate the correct Nx2 ColumnRecipes.
  • The UI successfully hides the complexity of building two coordinated JSON pipelines.

      • Internally track the Effective Row Type resulting from this modifier (queried from the backend descriptor).
    • Step B: Data Aggregation (Required). Prompt: “What data do you want to extract?”

  5. Add frontend tests for the UI Stitcher logic to ensure that selecting specific combinations yields the exact same raw ColumnRecipes as the JSON backend.

Exit criteria:

  • Users can mix and match row geometries (Step A) with data extraction logic (Step B) using a guided, wizard-like UI.
  • The UI safely prevents illegal combinations (e.g., Range Reduction on an Event row) by filtering Step B options based on Step A’s output.
  • Combinatorial explosion of UI presets is completely eliminated; the UI is highly composable.
  • The TensorDesigner list view accurately displays the generated columns.

Phase 9g: Polymorphic Preset Architecture and JSON DTOs

Status: done.

Goal: Refactor the monolithic ColumnRecipePresetRegistry into a modular architecture that separates behavioral execution (the Strategy pattern) from serialization (Flat DTOs for reflect-cpp). This allows complex presets to be defined in their own C++ files with custom UI callbacks, while enabling simple presets to be data-driven.

Tasks:

  1. Define Polymorphic Interfaces:
    • Create IRowModifier and IColumnAggregator base classes replacing the std::function structs.
    • Include standard metadata methods (id(), parameters(), expand()).
    • Include optional UI hook methods (e.g., virtual std::vector<std::string> getDynamicOptions(std::string const& field_name) const) to support dynamic AutoParam combo boxes without hardcoding UI logic into the registry.
  2. Refactor Existing Complex Presets:
    • Extract complex presets (like MultiPointXyAggregator) into their own .hpp/.cpp files implementing the new interfaces.
    • Update the registry to store std::unique_ptr<IColumnAggregator> and std::unique_ptr<IRowModifier>.
  3. Define Flat DTOs for JSON Presets:
    • Create JsonColumnPresetDto (and a Row Modifier equivalent) as flat, inheritance-free structs designed specifically for reflect-cpp parsing. These structs will hold id, ParameterSchema, and raw JSON template strings (e.g., pipeline_json_template).
  4. Implement the JSON Preset Strategy:
    • Create a JsonColumnAggregator : public IColumnAggregator class that accepts a parsed JsonColumnPresetDto in its constructor.
    • Implement expand() to perform simple string replacement, injecting user-provided parameters into the DTO’s JSON templates.

Exit criteria:

  • The registry monolithic file is eliminated; presets are modularized into independent files.
  • reflect-cpp serialization boundaries are strictly separated from C++ behavioral polymorphism.
  • Custom C++ presets can provide specialized UI behaviors (like populating data keys) via interface methods.
  • The foundation is laid to load simple presets from JSON files (Phase 10).

Phase 10: Preset Library Files and User Authoring

Goal: Distribute Neuralyzer with useful built-in JSON recipe generators and let users author, save, and import their own preset definitions using a library pattern.

Tasks:

  1. Add Qt-free helpers for tensor column preset files, scanning default directories ({config_dir}/presets/tensor_design/columns/ for users and resources/... for bundled).
  2. Implement catalog initialization that parses JSON files into JsonColumnPresetDto via reflect-cpp, wraps them in JsonColumnAggregator classes (from Phase 9g), and registers them.
  3. Implement load/save/delete for user preset JSON files.
  4. UI Save Workflow: Add a “Save as Custom Preset…” action in the TensorDesigner Advanced Pipeline editor.
  5. In the Save dialog, allow users to name the preset and declare simple parameters (e.g., exposing a window offset as an int).
  6. Serialize the resulting JsonColumnPresetDto to the user’s config directory so it appears in the “Add Preset” dialog in future sessions.
  7. Reject duplicate preset IDs across bundled and user entries in the initial implementation.
  8. Add tests for path helpers, catalog merge behavior, load/save/delete, duplicate ID policy, and template expansion.

Exit criteria:

  • Users can parameterize and save custom JSON pipelines directly from the UI, generating reusable template files.
  • The preset library correctly loads and seamlessly integrates User JSON presets alongside complex C++ Built-in presets.
  • User presets do not silently override bundled presets; lab-specific variants use unique IDs until explicit namespacing is introduced.

Verification Checklist

  • Existing JSON without row_pipeline_json produces unchanged tensors.
  • Empty row_pipeline_json is identity.
  • row_pipeline_json round-trips through parse and serialize.
  • DIS row-pipeline output must match source row count.
  • DES sample-time output must match source row count.
  • Iterable binding sources must match source row count.
  • Overlapping windows remain separate rows.
  • Generated gather windows use IntervalLayout::Overlapping where needed.
  • PipelineValueStore-backed normalization uses the marker for the current row, not the gather window start.
  • Cross-timeframe gathers match expected source query bounds.
  • interval_property columns remain source-gather-free.
  • The offset string-search compatibility path is removed after replacement.
  • Preset expansion and equivalent raw recipes produce the same values.
  • Bundled and user preset library entries load and expand correctly.
